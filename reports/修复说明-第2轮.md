## 二、逐条修复说明

### H1 · 高 · 网络请求同步阻塞 GUI 主线程

- **问题**（评审报告 H1 / 与 M5 同源）：
  `ui/main_window.py` 的 `_on_query` 在 GUI 主线程内同步调用
  `service.get_weather()`，其内部是阻塞式 `requests.Session.get`（超时最长约 8s）。
  无网/弱网时窗口直接冻结至多 8 秒，断网降级演示（SPEC A3）观感受损。

- **改动文件:位置**：
  1. `weather_app/ui/query_runner.py`（全部新增）；
  2. `weather_app/ui/main_window.py` → `__init__`（约 52–70 行）、`_on_query`（约 190–214 行）、
     新增 `_on_query_success` / `_on_query_error`、`_set_querying`。

- **修复做法**：
  1. **执行器抽象（`QueryRunner`）**：统一接口
     `run(service, day, use_online, on_success, on_error) -> None`；
     `on_success(record, last_fallback: bool)` 中 `last_fallback` 为查询完成瞬间
     从 service 读取的降级标记**快照**（由执行器回传，界面不再回调时再读 service 共享状态）；
     `on_error(exc: Exception)` 承接一切异常。
  2. **`SyncQueryRunner`**：当前线程立即执行并同步回调——**专供测试注入**，
     回调与查询在同一调用栈内完成，断言无需等待事件循环，结果完全确定。
  3. **`ThreadQueryRunner`**（真实应用默认）：
     - 每次查询创建一个一次性 `_WeatherWorker(QThread)`，在**后台线程**调用
       `service.get_weather`，随后读取 `last_fallback` 快照；
     - 结果/异常经 `succeeded(record, last_fallback)` / `failed(exc)` 信号发出；
       接收方（runner 本体）位于主线程，Qt 自动连接判定为**队列连接**，
       回调必然被投递回主线程后才执行 —— 界面操作始终在主线程；
     - **线程安全退出**：`finished` 槽中 `wait()`（确保完全退出）+ `deleteLater()`（线程结束后再析构），
       并清理 `_thread` 引用；慢查询在途时**忽略新的启动请求**（`isRunning()` 检查），
       同一时刻最多一个在途查询。
  4. **`MainWindow`**：
     - `__init__(self, service=None, runner=None, parent=None)`：`runner` 缺省为
       `ThreadQueryRunner(parent=self)`（真实应用异步）；允许注入 `SyncQueryRunner`；
     - `_on_query`：先判忙碌标记（`_querying`，忙碌期间忽略再次点击），随后
       `_set_querying(True)`（禁用按钮 + 文案「查询中…」）→ `runner.run(...)`；
       执行器自身抛错时走兜底恢复；
     - `_on_query_success`：设置 `_current_record` → `_render` → 按来源/降级分支提示
       → `finally` 恢复按钮；
     - `_on_query_error`：按 `DateOutOfRangeError` / `WeatherUnavailableError` /
       其他异常三类给出既有友好文案 → `finally` 恢复按钮。

- **既有对外行为保持清单**（逐项与旧版对齐，已行为抽检确认）：
  - 错误文案：「所选日期超出可查询范围（支持 1940-01-01 至未来 16 天），请重新选择。」
    /「天气数据暂时不可用：…」/ 兜底「查询失败：…」逐字不变；
  - 降级提示「已自动降级：当前展示「离线示例数据」。」（状态栏 8000ms）、
    离线「当前展示「离线示例数据」（未启用在线数据）。」（5000ms）、
    在线成功清空提示 +「已获取在线天气数据。」（5000ms）不变；
  - 来源标签由 `render_record` 渲染，不受影响；
  - 单位切换仍只重渲染 `_current_record`，**不重新请求**；
  - `_current_record` 语义：仅查询成功时更新，失败不覆盖旧结果；
  - `use_online` 在点击瞬间快照并贯穿该次查询的提示判定（与旧版读取时机一致）。

## 三、如何保证测试确定性

1. **注入式执行器**：单测构造 `MainWindow(service=fake, runner=SyncQueryRunner())` 后，
   `_on_query()` 返回时回调已执行完毕，「调用 → 断言」保持原有同步风格，
   不引入 `processEvents`/sleep 等不确定等待。
2. **完全相同的回调口径**：`SyncQueryRunner` 与 `ThreadQueryRunner` 对
   「成功回调 `(record, last_fallback)`、失败回调 `(exc)`、异常永不外抛打断界面」
   的语义逐字一致——测试用同步执行器验证的是与真实异步完全相同的代码路径（`_on_query`
   之后的渲染/提示/恢复逻辑共用），只有「执行时机」被替换。
3. **忙碌态可确定性测试**：`SyncQueryRunner` 执行期间按钮保持「禁用 + 查询中…」，
   服务替身可在 `get_weather` 内直接断言 `query_button.isEnabled() is False`（B05 用例口径不变）；
   「忙碌期间忽略重复点击」可用自建「手动执行器」（记录回调、由测试手动触发）在
   无事件循环下确定地验证。
4. **异步路径可确定性测试**：如需覆盖 `ThreadQueryRunner`，用 `qapp` 夹具 +
   `QApplication.processEvents()` 循环收敛（不依赖固定 sleep），本报告自检中已验证
   「service 在后台线程执行、回调回到主线程、线程 finished 后 `_thread` 清空」。
5. **无真实网络**：执行器只依赖注入的 service 替身；线程路径亦不触网。

**测试侧需要的对应调整（由 TestEngineer 负责，本轮未动测试文件）**：
现有 `tests/test_main_window.py` 中查询类用例需在构造时注入同步执行器，例如
`MainWindow(service=svc, runner=SyncQueryRunner())`
（`from weather_app.ui.query_runner import SyncQueryRunner`，或
`from weather_app.ui import SyncQueryRunner`）；其余断言无需改动。
